# AGENT_ONBOARDING — 새 직원·새 AI 투입, 퇴사·부재

규정 v3.13 · 2026-11-07 · 사람·AI 투입·교체·회수 또는 규정 변경 감지 시 해당 장만 읽는다. 평소 업무 규칙은 `BM_CORE.md`.

## 1. 모든 AI에 넣을 시작 지시 (부트스트랩)
어떤 AI든 BM 업무를 하려면 설정(사용자 지침·프로젝트 지침·플러그인·스킬)에 아래 뜻이 들어가 있어야 한다. 이 지시가 없으면 조약이 적용되지 않는다.

> 매 BM 업무 요청 시작에 STARTER 현재 버전을 재확인하고, 변경 또는 적용 버전 미상이면 최신 0장과 필요한 변경 규정을 적용한다. 자기 BM 설정 갱신은 1-1장을 따르며, 설정 저장 불가여도 최신 원본 적용을 우선한다. BM 업무는 Google Shared Drive `BM` 루트의 `BM_STARTER`를 먼저 읽고 그 0장 규칙대로 일한다(매번 읽는 규칙은 0장뿐, GitHub `BM_CORE`는 세부가 필요할 때만). 조회만 할 때는 INDEX `접속요약`(또는 `열린할일`) 탭과 `신규메일` 탭만 읽는다. 프로젝트를 만들 때는 READ·LOG·부록 3종을 기본 생성하고, 부록은 READ가 참조한 필요한 탭·구간만 읽는다. 메일 담당 AI는 OPS_MAIL에 따라 INDEX `메일수집` 탭을 먼저 읽고 판단하며, 다른 AI는 `메일수집`을 읽지 않는다. 할 일은 INDEX `할일` 탭에만 쓴다. 기록은 지시한 사람의 실명으로 하고, 내가 대신 적은 줄에는 실명 뒤에 `(도구명 기록)`을 붙인다. 접근할 수 없는 시스템은 추정하지 말고 실패로 보고한다.

현재 설정 위치
- Claude: 플러그인 `비엠업무`(호출: `/비엠업무` 또는 '비엠접속'·'비엠업무'·'BM접속'). 본문 원본은 `skills/bm-work/SKILL.md`.
- ChatGPT(Alex): ChatGPT 프로젝트·맞춤 지침에 위 문장을 넣는다(2026-10-28 v3.5 반영 완료). Codex용 스킬은 `skills/bm-work`.
- Gemini: Gem 지침(또는 Workspace 사용자 지침)에 위 문장을 넣는다(2026-10-28 v3.5 반영 완료). Google Drive 접근이 켜져 있어야 STARTER를 읽는다.
- 공통: GitHub 링크를 못 여는 AI도 STARTER 0장(필수 규칙 요약)만으로 같은 규칙이 적용된다. Drive 접근 자체가 없는 AI는 BM 업무에 쓰지 않는다.
- 새 AI: 위 문장을 넣고, 아래 3장 콜드스타트 테스트를 통과한 뒤 투입한다.

## 1-1. 변경 자동 수용 — 직원의 전달 없이 접속 시 갱신

1. 매 BM 업무 요청 시작(같은 채팅의 후속 요청 포함)에 STARTER의 현재 규정 버전을 다시 확인한다. 부분 조회가 되면 제목·현재 규정 줄만, 안 되면 STARTER를 읽는다. AI의 마지막 적용 버전과 같으면 이미 읽은 규칙을 재사용한다. 처음이거나 마지막 적용 버전이 불명이면 최신 0장 전체를 적용한다.
2. 버전이 다르면 최신 0장을 읽고, 마지막 적용 버전 이후 CHANGELOG 항목의 변경 파일·영향을 확인한다. 여러 버전을 건너뛰면 중간 변경도 확인한다. 변경된 파일 중 자기 역할·현재 업무에 필요한 최신 장만 읽는다. CHANGELOG를 읽을 수 없어도 최신 0장은 적용하며, 필요한 세부 원본을 못 읽으면 그 규칙에 의존하는 작업만 멈추고 실패를 보고한다. 번호만 보고 규칙을 추정하지 않는다.
3. 낡은 스킬·메모리·이전 대화의 BM 규칙은 최신 공식 원본보다 우선하지 않는다. 현재 업무에 최신 규칙을 먼저 적용한다. BM용 자기 설정을 수정하는 기능·권한과 사용자/호스트 정책이 허용하면, 관련 부분만 갱신하고 재조회한다. 무관한 사용자 메모리·다른 스킬·직원 권한은 바꾸지 않는다. 호스트가 승인을 요구하면 우회하지 않는다.
4. 자기 스킬·메모리에는 규칙 전문을 복제하지 않는다. STARTER 입구·공식 원본 링크와 `BM 적용 버전 / 확인일 / 설정 동기화 상태`만 최소 저장한다. 버전 번호는 접속 확인을 생략하는 근거가 아니다. BM용 장기 저장이 불가능하면 현재 세션에서만 적용 상태를 유지하고 다음 세션도 처음부터 STARTER를 확인한다.
5. 설치형·관리형 플러그인의 갱신은 그 도구의 정식 업데이트 경로로만 한다. 읽기 전용 설정·중앙 배포·승인이 필요하면 INDEX `업데이트요청`에 같은 사람·도구·목표 버전 요청이 있는지 확인 후 없을 때만 등록한다. 공개 GitHub에 직원·계정 정보를 남기지 않는다. 요청을 쓸 수 없으면 설정 갱신 미완료 사유와 필요한 조치만 보고한다. 직원에게 규칙을 다시 설명하거나 전달하게 하지 않는다.
6. `규정 적용`과 `설정 저장`은 구분한다. 적용 버전은 실제 필요한 규정을 읽어 적용한 뒤만 기록하고, 설정 동기화 완료는 저장 후 재조회한 뒤만 표시한다. 변경 감지 시에만 `BM vX 적용 / 설정 동기화 완료·불필요·미완료(사유)`를 짧게 알린다. 변경이 없으면 별도 보고·요청 행을 만들지 않는다.
7. STARTER를 못 읽으면 최신 확인 실패로 보고하고 과거 기억으로 확정·쓰기를 진행하지 않는다. 종료된 세션이나 실행 중이 아닌 AI에 변경을 밀어 넣는 기능은 아니다. 다음 업무 요청 때 최신화를 수행한다.

시스템관리의 배포 순서: GitHub 관련 원본·CHANGELOG 저장 및 재조회 → STARTER 0장·현재 버전 동기화 및 재조회 → 필요한 정식 플러그인 배포. 필수 시작 지시에는 특정 버전 번호를 고정하지 않고 아래 공통 입구를 유지한다. 직원 최초 투입 때 한 번 설정하고 테스트한다.

## 2. 투입 체크리스트
1. 실명·역할 등록: Drive `BM_STARTER` 2장 인원 목록과 Airtable `접근권한`에 실명·역할·사용 AI 도구를 기록한다. AI는 인원 목록에 올리지 않는다(사람이 쓰는 도구).
2. 계정: 직원은 개인 업무 계정으로 Drive·Sheets에 접속한다. `info@`는 대외 메일 전용 계정이며 공용 로그인으로 쓰지 않고, 필요한 직원은 Gmail 위임으로 접근한다.
3. 권한 부여(대표 승인): Shared Drive `BM` 멤버, INDEX 편집, 필요 시 Airtable·Docswave·Canva·Calendar. info@ 메일 업무가 필요하면 비밀번호 공유가 아니라 Gmail 위임으로 부여하고 OPS_MAIL 7장(사람이 하는 일)을 안내한다.
4. Airtable `접근권한`에 실명·역할·실제 확인된 접근수준·허용 범위·확인일 기록 (`ops/OPS_ACCESS.md`).
5. 역할 지정: 프로젝트 책임자·참여자를 READ 1장 `참여` 줄과 INDEX `담당자`에 반영.
6. AI 부트스트랩 설정(1장) 후 콜드스타트 테스트(3장).
7. 시스템관리 역할은 자동 승계되지 않는다. 대표가 별도로 지정하고 `BM_STARTER` 2장 인원 목록에 적는다.

## 3. 콜드스타트 테스트 (정상 시작 판정)
이전 대화를 모르는 상태에서 STARTER만 받고 아래에 답하면 통과다.
- AI 규정 원본과 매번 읽을 파일은? / 프로젝트 목록·등록 대기는 어디서 보나?
- 특정 프로젝트의 Drive 폴더·READ·현재 상태·다음 할 일은?
- 기록은 누구 이름으로 남기나? 내 권한과 INDEX에서 고칠 수 있는 열은?
- 계정·접근정보는 어디서 보나? 지금 접근할 수 없는 시스템은?
- 이전 적용 버전보다 STARTER가 새로우면 직원 설명 없이 변경 장을 찾아 적용하는가? 여러 버전 건너뛰기·버전 미상·설정 읽기 전용·STARTER 접근 실패도 구분하는가?
- 현재 규정 적용과 스킬/메모리 저장 결과를 분리하고, 변경 없는 재접속에서 중복 요청을 만들지 않는가?

## 4. 퇴사·장기부재·AI 교체
1. 담당 할 일·책임 프로젝트를 다른 사람에게 재배정하고 각 프로젝트 LOG에 남긴다.
2. INDEX `담당자`를 갱신한다(시스템관리).
3. Drive·Sheets·Airtable·Docswave·Canva 권한과 info@ Gmail 위임을 회수하고 Airtable `접근권한`을 갱신한다.
4. 과거 LOG·READ의 실명 기록은 고치지 않는다(작성자 식별 유지). STARTER 인원 목록에서는 '퇴사'로 표시한다.

## 5. 접속 안내 문구
- 전부 성공: `비엠에 접속했습니다. BM 기본 지침을 확인했습니다.` + 진행 프로젝트 요약 + `오늘 뭐부터 할까요?`
- 일부 실패: 성공한 시스템과 실패한 시스템을 나눠 말한다. 예) `STARTER와 GitHub 규정은 확인했습니다. Airtable은 접근권한을 확인하지 못했습니다.`
- 확정 사항은 자동 저장하므로 사용자에게 저장 명령을 요구하지 않는다.
