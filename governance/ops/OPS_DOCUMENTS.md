# OPS_DOCUMENTS — 문서관리

규정 v3.16 · 2026-11-15 · 공통 운영. 대장 위치·내부 ID는 비공개 STARTER / INDEX 공통문서에서만 확인한다.

## 1. 별도 지시 없이 적용
모든 AI는 STARTER를 읽은 뒤 문서 찾기·생성·수정·복사·이동 업무에서 INDEX 공통문서의 `BM_문서관리대장`을 사용한다. 일반 할 일 조회 때 전체 문서대장을 읽지 않는다. 문서 업무에서는 실행상태와 해당 행만 확인하고 필요한 원본을 연다. 미수집·오류·접근실패를 `자료 없음`으로 단정하지 않는다. 지도에 없을 때만 필요한 범위를 검색하고 찾은 파일ID로 등록·재조회한다.

결과물을 저장하면 명령을 기다리지 않고 같은 파일ID 행을 갱신한다. 새 파일·복사본은 새 ID이며 승인·현재본 판정을 승계하지 않는다. 이름·경로가 바뀌어도 같은 ID는 같은 파일이다. 사람이 만든·복사·이동한 문서는 Drive 동기화 후 다음 자동 순회에서 관측한다. 수집 지연·오류 때 AI가 필요한 파일을 직접 확인하여 등록할 수 있지만 전체 수집 완료로 기록하지 않는다. 동일 ID 중복이 있으면 새 행을 추가하지 말고 충돌을 보고한다.

## 2. 원본과 대장
- 대장들은 공통 회사문서 폴더에 두고, 실제 자료는 기존 프로젝트·소속·공통 폴더에 둔다. 계약서·협약서도 해당 프로젝트 원본 위치를 유지한다. 프로젝트 없는 공문·견적은 공통 또는 소속 DOC의 기존 실무 위치를 사용하고 프로젝트ID를 억지로 만들지 않는다.
- 중앙 문서목록은 파일 탐색 지도다. 공문 번호·시행·발송 원장은 발행주체별 공문대장, 견적 발급 원장은 견적대장, 결재 증거는 결재·발송 탭이 맡는다. 서로 같은 사실을 재입력하지 않고 관리ID·파일ID·링크로 연결한다. 기존 공문대장은 원본 파일을 유지하며 연결한다.
- 서울/인천 등 발행주체와 연도별로 번호를 분리한다. 일부 기록만 보고 다음 번호를 추정하거나 누락을 완료 처리하지 않는다. 실제 번호·본문 불일치는 확인필요로 두고 임의 수정하지 않는다.
- 사업발굴은 기존 공통 사업발굴 폴더ID를 유지한다. 폴더 표시명 변경은 ID로 추적한다. 루트 이전·자동 재분류·폴더 생성은 이 규정의 자동 실행 범위가 아니다.
- 제안 단계 자료는 제안건ID로 연결하고 실행 확정 뒤 프로젝트ID와 연결한다. 전환 때 원본·제안 이력을 보존한다. 사업발굴 목록은 기존 INDEX를 원장으로 쓰고 제안건 탭에 중복 사업 목록을 만들지 않는다. 아직 없는 제안건ID는 다른 기존 ID와 대조한 후 발급한다.

## 3. 서식과 현재본
공통규정·서식의 문서서식 폴더 → 분야별 승인 서식 → 실무 위치에 복사하여 사용한다. 원본은 보존한다. 서식대장에 원본 링크·분야·사용판정·근거를 기록한다. 실제 발급 공문, 과거 예시, 개인정보 기입본을 표준 빈 서식으로 취급하지 않는다. 승인되지 않은 서식은 `검토 필요`. 폴더 정리·이름 변경은 별도 승인 범위다.

문서목록 A:I는 관측 사실, J:M은 업무확정·역할·현재본확인·근거다. 자동수집은 A:I만 갱신한다. 최신 수정일이 현재본·운영확정의 근거는 아니다. 현재본 확인에는 적용 용도·승인 또는 판단 근거·검증한 원본 버전/수정시각을 남긴다. 원본이 그 뒤 바뀌었으면 기존 현재본·결재 표시만 믿지 말고 다시 검증한다. 초기 참고 문서 본문을 최신처럼 고치지 않는다.

## 4. 공문 결재·날인·발송
초안 → 결재 요청 → 승인된 원본 버전 확인 → 발급번호 확정·날인 → 발송 → 발송 증빙. 결재는 사람 권한이며 승인과 발송은 별개다. 승인자·시각·승인 대상 버전·승인 근거를 기록한다. 수정됐으면 재승인한다. 날인·발송은 그 행위에 대한 지시와 승인 범위가 있어야 하며, 대장 등록이나 STARTER를 읽었다는 이유로 자동 수행하지 않는다. 취소번호는 재사용하지 않는다. 승인·확정·발송 완료를 AI가 추정하여 기입하지 않는다.

현재 구현은 기록·검색·수집 도구이며 공문 승인·발급을 강제하는 결재 엔진이 아니다. 자동 채번·자동 날인·자동 발송은 구현하지 않았다. Docswave 적용 전에는 대표가 원본과 승인 근거를 확인하고 진행한다.

## 5. 수집기와 실제 가동 상태
`integrations/document-registry/`의 Code.gs·매니페스트·설치안내를 사용한다. Drive 읽기 전용으로 문서 메타데이터를 15분 간격 전체 순회한다. 큰 목록은 페이지별 저장·재조회 후 체크포인트를 갱신하고 다음 예약 실행에서 재개한다. 완전한 시점 스냅샷이나 실시간 감시는 아니며 동시 변경은 다음 전체 순회에서 보완한다. 폴더 이동·이름 변경에 따른 하위 경로도 다음 순회에서 재확인한다.

스탬프·백업·아카이브 등 설정의 제외 폴더 하위는 제외하고 본문을 수집하지 않는다. 대장 자체도 제외한다. 기존 파일이 제외 폴더로 옮겨진 경우 탐색용 제목·링크·경로를 비운다. 휴지통·삭제·접근불가·외부 이동·미관측을 구분할 수 없으면 재확인 표시만 하며 원본 삭제·자동 정리하지 않는다. 수집기는 대외 발송 권한이 없다. 대표 계정 하나만 설치한다. 직원 접근 제어는 별도 Drive 권한 설계 때 적용한다.

코드 작성·로컬 테스트·구글 설치·권한 승인·트리거 생성·최초 전체 수집·예약 실행 성공은 별도 상태다. 실제 실행상태·설치 계정의 트리거·실행 기록을 확인하기 전 `자동 운영 중`이라 말하지 않는다. 도구에 설치 권한/기능이 없으면 코드와 설치 경로를 완성한 뒤 필요한 일회성 설치 조치를 보고한다. 다른 AI의 미접속 상태를 적용 완료로 기록하지 않는다.

## 6. 변경 공지·확인
문서관리뿐 아니라 메일·대장·자동화·연동·진입 경로 등 모든 시스템 운영 변경은 같은 버전의 AI 공지에 항상 남긴다. 대상별 실행 조치·확인 방법·설치/가동 상태·남은 조치·이전 공지를 기록한다. 각 AI는 다음 BM 진입 때 자기 대상 조치를 실제 권한 안에서 실행하고 자기 AI적용 행만 기록한다. 공지 게시가 미접속 AI의 백그라운드 실행이나 권한 부여를 뜻하지 않는다.

콜드스타트 검증: 새 AI에게 `문서 찾아줘` 또는 `공문 작성`만 준 상황에서 STARTER → INDEX 공통문서 → 중앙 대장 → 해당 원본으로 도달하고, 서식 사용판정·승인/발송 구분·미설치 상태를 확인하는지 검사한다.
