# OPS_PROJECT — 프로젝트 찾기·생성·INDEX·실행

규정 v3.9 · 2026-11-04 · 프로젝트를 찾거나 만들거나 INDEX를 고칠 때만 읽는다. 공통 규칙은 `BM_CORE.md`.

## 1. 찾기와 중복검사
INDEX에 없다는 이유만으로 프로젝트가 없다고 단정하지 않는다. 신규 생성 전 확인 순서:
1. INDEX `프로젝트` 탭 → 2. `업데이트요청` 탭의 등록 대기 → 3. `레거시_폴더` 탭 → 4. Drive 동일·유사 프로젝트

동일 후보로 보는 차이: 26↔2026, 띄어쓰기·괄호·특수문자, 약칭↔정식명칭, 핵심어가 같은 유사 사업명. 명백히 같으면 새로 만들지 않고, 확신이 없으면 묻는다. 레거시 폴더를 진행 프로젝트로 간주하지 않는다.

## 2. 생성
- 프로젝트 생성은 `[대표결정]`이 필요하다. 주관 조직·운영단위·계약·회계 관계가 불명확하면 먼저 확인한다.
- 이름(폴더명·INDEX `프로젝트명`): `YYYY_NNN_프로젝트명`. NNN은 그 프로젝트 ID의 끝 3자리(예: `BMS-2026-006` → `2026_006_…`)
- 위치: `BM/01_BM서울/02_BM서울_프로젝트/YYYY/` 또는 `BM/02_BM인천/02_BM인천_프로젝트/YYYY/`. 센터·거점 등 운영단위 프로젝트는 승인된 위치를 확인한다.
- 기본 하위폴더: 01_기획 / 02_대외·계약 / 03_실행 / 04_홍보·디자인 / 05_성과·결과 / 06_사진·영상 / 90_참고자료. 필요한 폴더만 만든다.
- READ·LOG: `templates/PROJECT_READ_TEMPLATE.md` 기준 Google Docs 2개, 제목 `YYYY_프로젝트명_READ`·`YYYY_프로젝트명_LOG`. READ 6장 첫 줄에 LOG 링크. 확인된 값만 기록한다.
- 등록: 시스템관리는 `프로젝트` 탭에 직접 등록하고 ID를 부여한다. 그 외는 `업데이트요청`에 신규 등록 요청을 남긴다. 시스템관리 권한이 확인되지 않으면 등록 대기로 남긴다.
- 기존 프로젝트는 새 규칙과 다르다는 이유만으로 자동 이동하지 않는다.

## 3. BM_PROJECT_INDEX
### 탭
- `프로젝트`: 정규 프로젝트 공식 목록 · `공통문서`: 프로젝트가 아닌 살아있는 문서(플랫폼 READ·LOG, GUIDE, 대장) 목록 · `업데이트요청`: 신규·변경 요청 큐 · `레거시_폴더`: 과거 프로젝트성 폴더 위치 · `사업발굴`: 프로젝트가 되기 전 사업 기회 목록(종료·보류는 `사업발굴_보관`) · `신규메일`: 메일 담당 AI가 갱신하는 보기 전용 스냅샷
- `사업발굴` 열: 발굴ID(`O-001`부터) / 출처구분(기본계획·업무계획·공고·정보) / 기관 / 계획·사업명 / BM 관련 내용 한 줄 / 예상 시기 / 예산 규모 / 적합도(상·중·하·미판단) / 상태(관찰→검토→준비→프로젝트 전환, 보류·종료) / 다음 확인일 / 원문·요약 링크 / 프로젝트ID / 수정(날짜·실명). 한 기회 한 줄, READ·LOG는 만들지 않는다.
- 원문(스캔 PDF 등)은 `00_BM공통/03_사업발굴`에 `YYYY_기관_계획명_원문`으로 두고, 처음 등록할 때 한 번만 읽어 `_요약` Google 문서(2,000자 이내: BM 관련 과제·예산·연차 일정·담당 부서·근거 쪽수)를 만든다. 이후에는 요약만 읽는다.
- 신청이 대표 결정되면 프로젝트를 생성하고, 그 줄의 상태를 `프로젝트 전환`, 프로젝트ID를 적는다. 요약 문서는 새 READ 6장에 링크한다. `다음 확인일`이 된 줄은 `접속요약` 탭 경고 칸에 자동 표시된다.
- `프로젝트` 탭 `메일 식별` 열: 메일을 프로젝트에 연결할 때 쓰는 기관명·도메인·고유 키워드. 프로젝트 생성 시 확인된 값만 채우고, 새 거래처·식별어는 `업데이트요청`으로 추가한다.
- `공통문서` 열: 문서명 / 역할(READ·LOG·GUIDE·부록) / 범위 / 링크 / 형식 / 관리자(실명) / 최종수정일 / 비고. 행 추가·삭제는 시스템관리 또는 대표 지시로 한다. 그 외는 `업데이트요청`.

### 프로젝트 ID
`조직코드-YYYY-NNN`. 조직(운영단위)별·연도별로 001부터 따로 매기고, 번호는 항상 3자리다.

| 조직코드 | 조직 |
|---|---|
| BMS | BM서울 |
| BMI | BM인천 |
| MCH | 마포 콘텐츠 허브 센터 (위탁 확정 시 사용 시작) |

- 새 조직·위탁센터 코드는 `[대표결정]`으로 정하고 이 표에 추가한다.
- 한번 부여한 ID는 이름·폴더가 바뀌어도 변경하지 않는다. 체계 자체를 바꾸는 일괄 전환만 `[대표결정]`으로 예외를 둔다(2026-10-22 `BM-2026-NNN` → 조직별 코드 전환, 대응표는 `CHANGELOG.md` v3.2).

### 열별 수정 권한
| 열 | 수정 가능 |
|---|---|
| 진행상태(기획·진행·보류·마감요청), INDEX 최종수정일, 수정자, 행 버전 | 해당 프로젝트 책임자(및 그 지시 AI), 시스템관리 |
| 진행상태의 종료·취소, 프로젝트 ID, 프로젝트명, 대외명·별칭, 주관 조직, 운영단위, 담당자, 메일 식별, Drive·READ URL, 신규 행 | 시스템관리만 |

- 수정 시 `INDEX 최종수정일`·`수정자`(실명, AI가 대신 쓰면 도구 표시)를 갱신하고 `행 버전`을 1 올린다.
- `다음 할 일` 열은 `할일` 탭에서 우선 3개를 자동으로 보여주는 수식이다. 직접 쓰지 않는다. 진행 경과·상세는 INDEX에 쓰지 않는다(READ 0장이 원본).

### 할 일 탭 (v3.4)
- `할일`: 할 일의 유일한 원본. 열: 할일ID / 프로젝트ID / 프로젝트명(자동) / 할 일 / 담당(실명, 미정 가능) / 우선(숫자, 작을수록 먼저) / 기한(YYYY-MM-DD) / 상태(`진행`·`할 일`·`대기`·`승인 필요`·`완료`) / 비고(대기 대상·선행조건) / 수정일 / 수정자(실명·도구).
- 할일ID: 조직코드 첫 글자+프로젝트 번호+순번(`S003-01`=BMS-2026-003의 1번, `I001-02`=BMI-2026-001의 2번). 한번 부여하면 바꾸지 않고, 고칠 때는 행 번호가 아니라 ID로 찾는다.
- 권한: 프로젝트 책임자·담당자(및 그 지시 AI)가 자기 프로젝트 행을 추가·수정한다. 행 삭제는 하지 않는다(완료로 표시).
- 보기(자동, 직접 쓰지 않음): `접속요약`=진행 중 프로젝트별 우선 3개 / `열린할일`=완료가 아닌 할 일 전체(프로젝트·우선 순) / `프로젝트` 탭 `다음 할 일` 열.
- 정리: 시스템 점검 때 `완료` 행을 `할일_보관`으로 옮긴다. 완료 사실은 프로젝트 LOG에 이미 남아 있다.
- 권한이 없는 변경은 `업데이트요청`에 한 요청당 한 변경으로 남긴다: 요청 ID `REQ-YYYYMMDD-짧은이름` / 프로젝트 ID / 요청일시 / 요청자(실명·도구) / 변경 필드 / 현재값 / 요청값 / 근거 URL / 처리상태 `대기`.
- 시스템관리는 처리 직전 INDEX 행·READ·근거를 다시 확인하고, 처리 후 `반영` 또는 `반려`와 처리자·처리일시를 기록한다. 같은 프로젝트의 요청은 행 버전 기준으로 순차 처리한다.

## 4. READ 운영 세부
- READ는 Project Memory File이며 계약·공문·결재 원본을 대체하지 않는다. 공식 원본과 충돌하면 공식 원본이 우선이고 READ를 정정한다.
- 확정된 변화만 기록한다: 일정·예산·담당·범위·결정·완료업무·다음 행동·핵심 링크·단계 변화. 대화 전체를 복사하지 않는다.
- 사용자가 미확정 내용 저장을 요청하면 `[제안]`·`확인 필요`로 구분해 기록한다.
- 값이 바뀌면 READ는 새 값으로 덮어쓰고, 이전 값·이유는 LOG 끝에 한 줄로 덧붙인다(LOG는 열지 않고 끝에 추가). 끝난 할 일은 `할일` 탭 상태를 `완료`로 바꾸고 LOG에 완료로 남긴다.
- 긴 작업은 중요한 확정이 생길 때마다 중간 저장한다. 완료보고 전 누락을 점검한다.
- 저장 실패: 원인 확인 → 안전한 재시도 → 계속 실패하면 복구할 내용을 대화에 남기고 `READ 저장 미완료`로 보고. 불확실한 생성은 존재 여부를 먼저 확인해 중복을 막는다.
- 6장은 서류 목록(`서류 · 상태 · 링크/위치`, 유형별 체크리스트는 `PROJECT_READ_TEMPLATE` 6장). 서류가 생기거나 상태가 바뀌면 그 줄만 고친다. 날짜가 붙은 진행 기록은 6장에 쓰지 않는다(결정은 4장, 경위는 LOG). 서류를 찾을 때 6장을 먼저 보고, 없을 때만 Drive를 검색한 뒤 찾은 서류를 6장에 추가한다.
- 같은 READ를 여러 사람·AI가 쓰면: 0장·상태는 책임자만, 나머지는 자기 줄만 고치거나 새 줄을 추가한다. 할 일 배정은 `할일` 탭 `담당`에 실명으로 적는다.

## 5. 이동·취소·삭제·정리
- 프로젝트 전체 이동은 승인 후 하고 INDEX·READ 링크를 점검한다.
- 기록이 있는 취소 프로젝트는 삭제하지 않고 `취소`로 관리한다. 공식 기록은 자동 삭제하지 않는다.
- 중복·임시파일은 삭제 후보와 보존 대상을 구분해 승인받고, 삭제 후 끊어진 링크가 없는지 확인한다.

## 6. 파일명·버전
- **현재 작업본은 1개만 둔다.** Google Docs/Sheets/Slides는 자체 버전기록을 사용하고, 현재본 파일명에는 `초안`·`v1`·`v2`·`검토안` 같은 순번·상태를 붙이지 않는다. 권장 현재본: `문서종류_프로젝트명`.
- 별도 파일을 남겨야 하는 중요한 시점만 상태 스냅샷을 만든다: `YYYYMMDD_문서종류_프로젝트명_검토본` / `승인본` / `제출본` / `운영확정본`.
- 현재본이 갱신되어 생긴 **일반 실무 초안·vN·검토안의 과거본**은 프로젝트 루트 `99_이전버전`에 임시 보관한다. 필요하면 그 안에 `01_기획` 등 원래 상위폴더명을 만들어 위치를 보존한다. AI는 경위 확인 지시가 없으면 `99_이전버전`을 읽지 않는다.
- 운영확정본·제출본 등 최종 사용본이 확인되고 해당 업무가 끝난 뒤, 대표가 `정리`·`마감`을 지시하면 `99_이전버전`의 일반 작업 초안은 삭제할 수 있다. **공식 제출본·승인본·공문·계약·협약·정산·회계·증빙·결과물은 삭제하지 않는다.**
- 시스템 규정·READ·LOG·GUIDE처럼 공식 구조 문서가 대체된 경우는 프로젝트 `99_이전버전`이 아니라 기존 BM_CORE의 98_아카이브·99_시스템백업 규칙을 따른다.
- 외부에서 받은 원본 파일의 버전명은 출처 증빙이므로 임의로 고치지 않는다. `최종2`·`진짜최종`·`복사본`·`(1)(1)` 식의 내부 파일명은 금지한다.
- Drive 루트에 개별 프로젝트·임시파일을 만들지 않는다. 여러 위치에 필요하면 복사보다 링크·바로가기.

## 7. 시스템별 사용
- Drive: 문서는 INDEX 링크로 열고, 새 파일을 만들기 전에만 동일·유사 파일을 검색한다. 실무자료·최종 산출물·READ의 공식 위치.
- Canva: 디자인 편집 원본. 중간 시안을 Drive에 반복 저장하지 않고 최종 승인·납품본만 Drive 정식 위치에 둔다.
- Docswave: 기안·품의·지출·인사·근태·급여·계약 원본. Drive에 행정문서 이중 원본을 만들지 않는다.
- Gmail: 대외 소통(발송 계정 `info@`는 메일 전용). Calendar: 공식 일정·행사·마감. Slack: 빠른 협의. Notion: 할 일·진척. 중요한 확정은 READ나 공식 원본에 반영한다.
- 외부 메시지 발송·공유는 사용자가 명시적으로 지시한 범위만 한다.
