# SYSTEM_HEALTH_CHECK

**버전:** v1.3  
**기준일:** 2026-10-15  
**목적:** BM Digital 1.0의 구조·링크·접근·저장 절차가 실제 시스템과 일치하는지 반복 점검한다.

## 1. 정상 기준

### Google Shared Drive 루트
루트에는 원칙적으로 다음 핵심 진입요소와 조직 폴더가 보인다.
- `BM_STARTER.md`
- `BM_PROJECT_INDEX` (Google Sheets)
- `00_BM공통`
- `01_BM서울`
- `02_BM인천`
- `98_아카이브`
- `99_시스템백업`

구형 AI 운영 MD는 루트 공식 원본으로 두지 않는다.

### 실제 프로젝트 경로
- `BM/01_BM서울/02_BM서울_프로젝트/YYYY/YYYY_프로젝트명`
- `BM/02_BM인천/02_BM인천_프로젝트/YYYY/YYYY_프로젝트명`

### 공식 원본
- AI 운영: Public GitHub `iceckorea-alt/BM-AI-SYSTEM`
- 프로젝트 목록: Google Sheets `BM_PROJECT_INDEX`
- PROJECT_READ 인스턴스: 각 Drive 프로젝트 폴더
- 접근정보: Airtable `BM_ACCESS_REGISTRY`
- 공식 행정: Docswave

## 2. 구조·링크 점검
1. STARTER가 존재하고 GitHub·INDEX·Drive·Airtable·Docswave 역할을 올바르게 안내하는가
2. GitHub main에 DIGITAL / AGENTS / ONBOARDING / HEALTH_CHECK / PROJECT_READ_TEMPLATE 최신본이 존재하는가
3. GitHub 운영문서와 실제 Shared Drive 경로가 일치하는가
4. GitHub 공개상태가 문서 설명과 일치하는가
5. Sheets의 `프로젝트`, `업데이트요청`, `레거시_폴더` 탭 역할이 운영규칙과 일치하는가
6. Sheets의 정규 프로젝트 행에서 Drive 폴더와 PROJECT_READ 링크가 열리는가
7. 등록 대기 프로젝트가 `업데이트요청` 탭에서 누락되지 않았는가
8. INDEX 상태와 READ 상태가 일치하는가
9. READ의 핵심 원본 링크가 살아 있는가
10. 브랜드·공통 READ가 구형 STARTER/INDEX/AGENTS 링크를 참조하지 않는가
11. 구형 운영문서가 LEGACY·백업으로 구분되어 현재 규정과 혼동되지 않는가

## 3. 저장 절차 점검
다음 시나리오를 실제로 검증한다.

### 3.1 확정된 작업 결과 저장
- 실제 결과물 파일이 저장됐는가
- PROJECT_READ에 확정된 결정·완료업무·현재상태·다음 행동이 반영됐는가
- 결과물 파일 위치와 READ 기록을 별도로 확인했는가
- 쓰기 후 READ를 다시 읽어 반영 여부를 확인했는가

### 3.2 변경 없는 업무
- 확정된 맥락 변화가 없다면 불필요한 READ 수정이 생략됐는가
- 완료보고에 `READ 변경 없음`이 표시됐는가

### 3.3 저장 실패
- 쓰기 실패 원인을 가능한 범위에서 확인했는가
- 안전한 재시도를 했는가
- 실제 업무 완료와 기록 미완료를 구분했는가
- 복구할 내용을 대화에 남겼는가

### 3.4 완료보고
다음 중 하나가 표시되는가
- `READ 저장·확인 완료`
- `READ 변경 없음`
- `READ 저장 미완료 — 사유와 복구할 내용`

## 4. 프로젝트 등록·다중 AI 점검
1. INDEX에 없다는 이유만으로 신규 프로젝트를 생성하지 않았는가
2. 등록 대기 `업데이트요청`과 Drive 동일·유사 프로젝트를 확인했는가
3. 일반 프로젝트 AI가 중앙 `프로젝트` 탭을 직접 수정하지 않았는가
4. 지정 시스템관리 AI·권한 있는 관리자만 중앙 등록을 처리했는가
5. 시스템관리 권한이 미확정이면 처리 대기로 남겼는가
6. 중앙 반영 시 프로젝트 ID·수정자·수정일·행 버전·요청 처리상태가 함께 갱신됐는가
7. 장기간 미처리 또는 동일 프로젝트의 충돌 요청이 남아 있지 않은가

## 5. READ·템플릿 정합성
1. GitHub PROJECT_READ_TEMPLATE 최신 버전을 확인했는가
2. 실제 READ의 Schema 표기와 실제 형식이 일치하는가
3. 버전 숫자만 올리고 구조를 바꾸지 않은 READ가 없는가
4. 필요한 프로젝트부터 완료·진행·대기·리스크·다음 행동을 구분해 보완했는가
5. 기존 결정·링크·변경이력이 보존됐는가
6. 일정·예산·도구명·모델명 등 변동 가능한 정보가 근거 없이 고정 사실로 남아 있지 않은가

## 6. 접근권한·직원정보 점검
1. Airtable `계정정보`에 비밀정보가 아닌 리소스 ID·설명만 저장되고 있는가
2. Airtable `접근권한`에는 시스템별 실제 확인 수준, 업무상 허용 범위, 확인 근거·미검증 사항이 기록돼 있는가
3. `계정정보`의 관리자 표기만으로 현재 AI 편집·관리 권한을 추정하지 않았는가
4. 연결 성공을 실제 편집·관리 권한으로 확대 해석하지 않았는가
5. 대장 기록 자체를 서비스 권한 부여로 오해하지 않았는가
6. GitHub는 Public 읽기 가능 상태인가
7. Shared Drive / Airtable / Docswave / Canva / Gmail·Calendar 등 필요한 시스템의 실제 접근 성공 여부를 각각 구분했는가
8. 일부 시스템 실패 시 전체 접속 성공으로 표현하지 않았는가
9. 직원 업무 연결정보와 개인 연락처·주소·급여 등 비공개 인사정보가 분리되어 있는가
10. 공식 인사·급여·계약 원본은 Docswave를 기준으로 유지되고 있는가
11. 직원 명부가 필요 확정 전 추정·선생성되지 않았는가
12. '대표 전용' 표기나 화면 숨김만으로 보안을 구현했다고 보고하지 않았는가
13. Airtable의 실제 Base/Interface/공유 권한으로 필요한 제한이 가능한지 검증했는가
14. 같은 Base에서 필요한 제한이 불가능하거나 미검증이면 별도 Base 등 분리 대안을 제안했는가

## 7. 인증정보·민감파일 점검
일반 지침·READ 탐색에서 인증정보로 보이는 파일의 **내용을 열지 않는다**.

점검 방식:
- 파일명·위치·MIME 등 메타데이터만 확인
- `client_secret*.json`, credentials, token, 비밀번호, 복구코드 등 민감 가능성이 있는 파일은 일반 검색·요약 대상에서 제외
- 발견 시 READ·플러그인·Public GitHub에 내용을 복사하지 않음
- 보관 위치·접근범위 정비 필요성을 별도 제안
- 승인 없는 삭제·이동·권한 변경 금지

## 8. 플러그인 전 점검
- 플러그인 제작·설치·배포가 완료되지 않았다면 완료된 것처럼 기록하지 않는다.
- `@비엠접속`은 표시명·호출 후보일 뿐 정확한 호출 문법으로 확정하지 않는다.
- 플러그인에 규정 전체 사본을 고정 저장하기보다 최신 공식 원본을 읽는 절차를 설계한다.
- 대표님용 플러그인에 시스템관리 역할을 부여할지는 별도 결정사항으로 유지한다.
- 기존에 대표 승인으로 중앙 INDEX를 반영한 이력이 있더라도 새 채팅·새 AI·플러그인에 영구 시스템관리 권한이 자동 승계됐다고 보지 않는다.
- 자동 저장, 저장 실패 복구, 부분접속 안내는 플러그인 제작 후 실제 실행으로 별도 검증한다.

## 9. 이상 발견 시
- 안전하게 바로잡을 수 있는 링크·표기·단일 원본 불일치는 즉시 수정한다.
- 삭제·공유권한·대량이동·법적/회계 사실 변경은 승인 후 처리한다.
- 권한 때문에 검증할 수 없는 항목은 `미검증`으로 명시한다.
- 점검 완료를 보고할 때 `확인 완료 / 수정 완료 / 미검증 / 사용자 결정 필요`를 구분한다.
