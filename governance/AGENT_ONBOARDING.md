# AGENT_ONBOARDING

**버전:** v1.2  
**기준일:** 2026-10-15  
**목적:** BM을 처음 맡는 사람 직원 또는 AI 직원이 과거 채팅·대표의 기억에 의존하지 않고 공식 원본에서 업무를 시작하기 위한 공통 진입 절차.

## 1. 필수 접근환경
업무 범위에 따라 아래 접근권한이 필요하다.

1. Google Shared Drive `BM`
   - `BM_STARTER.md`, 프로젝트 폴더, 실제 PROJECT_READ
2. Public GitHub Repository `iceckorea-alt/BM-AI-SYSTEM`
   - AI 운영규칙·Skills·자동화·연동문서
3. Google Sheets `BM_PROJECT_INDEX`
   - `프로젝트`, `업데이트요청`, `레거시_폴더`
4. Airtable `BM_ACCESS_REGISTRY`
   - `계정정보`: 계정·SNS·서비스 접근 기준정보
   - `접근권한`: 사람 직원·AI 직원별 시스템 접근 확인대장
5. 업무에 필요한 경우 Docswave / Canva / Gmail / Google Calendar

GitHub는 공개 읽기가 가능하지만 Google Drive, Sheets, Airtable, Docswave 등은 별도 연결 또는 계정 권한이 필요할 수 있다.

접근권한이 없는 시스템은 우회하지 않는다. `자료가 없다`고 단정하지 말고 접근권한 부족으로 보고한다.

## 2. 새 채팅의 첫 실행
1. Google Shared Drive `BM` 루트의 `BM_STARTER.md`를 읽는다.
2. GitHub `governance/BM_DIGITAL_1.0.md`와 `governance/BM_AI_AGENTS_.md` 최신본을 확인한다.
3. 프로젝트 업무이면 Google Sheets `BM_PROJECT_INDEX`에서 `프로젝트`, 등록 대기 `업데이트요청`, 필요 시 `레거시_폴더`를 확인한다.
4. 해당 프로젝트의 PROJECT_READ를 읽는다.
5. 브랜드·분야별 기준과 실제 업무 원본을 확인한다.
6. 업무를 수행한다.

INDEX에 없다는 이유로 프로젝트가 없다고 판단하지 않는다. 등록 대기 요청과 Drive의 동일·유사 프로젝트를 확인한다.

동일 채팅에서 이미 확인한 지침은 매 작업마다 전부 반복해서 읽지 않는다. 업무 범위가 바뀌거나 변경 가능성이 있을 때 재확인한다.

수정 직전에는 대상 READ·INDEX·실제 원본의 최신 상태를 다시 확인한다.

## 3. 새 직원·새 AI에 넣을 최소 시작지시
다음 의미가 항상 적용돼야 한다.

> BM 업무를 시작할 때 Google Shared Drive 'BM' 루트의 BM_STARTER.md를 먼저 확인한다. 이어서 Public GitHub BM-AI-SYSTEM의 최신 상위 기준과 AI 실행규칙을 확인한다. 프로젝트 업무는 BM_PROJECT_INDEX의 프로젝트·등록 대기·레거시 위치를 필요한 범위에서 확인한 뒤 해당 PROJECT_READ와 실제 원본을 읽는다. 중앙 INDEX의 프로젝트 탭은 직접 수정하지 않고 변경이 필요하면 업데이트요청 탭에 남긴다. 접근할 수 없는 시스템은 추정하지 말고 권한 부족을 보고한다.

## 4. 접속 안내 문구
### 실제 접속과 필수 지침 확인에 성공
> 비엠에 접속했습니다. BM 기본 지침을 확인했습니다. 진행할 업무를 말씀해 주세요. 작업 결과를 기록하려면 ‘작업 결과 저장’이라고 입력해 주세요.

자동 중간저장 또는 종료저장이 이미 끝난 경우 저장 명령을 다시 요구하지 않는다.

### 일부 시스템 접근 실패
성공한 시스템과 실패한 시스템을 구분한다.

예:
> GitHub 운영규칙과 BM_STARTER는 확인했습니다. Airtable은 현재 접근권한을 확인하지 못해 계정·접근정보는 검증하지 못했습니다.

전체 접속에 성공하지 않았다면 `비엠에 접속했습니다`만으로 전체 성공처럼 표현하지 않는다.

### 작업은 끝났지만 READ 저장이 남음
> 작업을 완료했습니다. 현재 작업 결과는 READ에 미저장 상태입니다. ‘작업 결과 저장’이라고 입력하면 작업 결과와 현재 상태를 기록합니다.

### 저장과 재확인 완료
> 작업 결과를 저장하고 확인했습니다.

해당 PROJECT_READ 링크와 실제 결과물 위치를 함께 안내한다.

## 5. 저장 명령
`작업 결과 저장`, `현재 상태 저장`, `현재 상태 업데이트`, `READ 업데이트`는 같은 의미다.

저장 대상:
- 확정된 결정
- 실제 완료된 업무와 결과물 링크
- 현재 진행상태·미결사항
- 다음 해야 할 일

쓰기 성공 응답만으로 완료라고 판단하지 않고 최신 READ를 다시 읽어 확인한다.

## 6. 다중 AI·INDEX 원칙
- 중앙 `프로젝트` 탭은 지정 시스템관리 AI 또는 권한 있는 관리자만 수정한다.
- 일반 직원 AI·프로젝트 AI는 변경이 필요하면 `업데이트요청` 탭에 등록한다.
- AI는 스스로 시스템관리 역할을 부여하지 않는다.
- 담당 시스템관리 권한이 확인되지 않으면 등록 대기로 보고한다.
- 같은 프로젝트에 여러 AI가 참여하면 PROJECT_READ 대표 작성자를 정하고 동시 덮어쓰기를 피한다.
- 채팅 기억을 공식 기억으로 사용하지 않는다.

## 7. 접근권한 확인
새 직원·새 AI를 실제 투입하기 전 Airtable `접근권한` 테이블에 실제 확인된 접근수준만 기록한다.

- 연결 성공만으로 읽기·편집·관리 권한을 확대 해석하지 않는다.
- 서비스의 `관리자` 계정이 존재한다는 사실만으로 현재 AI에게 편집·관리 권한이 있다고 판단하지 않는다.
- `접근권한`에는 시스템별 실제 확인 수준, 업무상 허용 범위, 확인 근거, 미검증 사항을 남긴다.
- Airtable 대장에 기록했다고 실제 서비스 권한이 부여된 것은 아니다.
- 대표님용 플러그인의 중앙 INDEX 시스템관리 역할은 별도 결정 전까지 자동 부여하지 않는다.

직원 확대 시에는 이름·직책·업무용 이메일·담당 프로젝트 같은 업무 연결정보와 개인 연락처·주소·급여 같은 비공개 인사정보를 분리한다. 공식 인사·급여·계약 원본은 Docswave를 기준으로 하고, 직원 명부는 필요가 확정되기 전 미리 만들거나 추정해 채우지 않는다.

'대표 전용' 표기나 숨김 화면만으로 접근 제한이 됐다고 보지 않는다. 실제 Airtable Base/Interface/공유 권한으로 제한 가능 여부를 확인하고, 같은 Base에서 필요한 분리가 구현되지 않으면 별도 Base 등 대안을 검토한다.

## 8. 인증정보 취급
일반 업무 중 `client_secret*.json`, credentials, token, 비밀번호, 복구코드 등 인증정보로 보이는 파일은 열거나 내용을 복사하지 않는다.

발견 시:
- 내용 열람 금지
- READ·플러그인·Public GitHub 복사 금지
- 보관 위치·접근범위 정비 필요성만 보고
- 승인 없는 삭제·이동·권한변경 금지

## 9. 플러그인 관련 현재 상태
이 문서는 플러그인 제작·설치·배포 완료를 뜻하지 않는다.

`@비엠접속`은 향후 표시명·호출 방식 후보일 뿐이며, 설치되었거나 정확한 호출 문법이 확정된 것처럼 안내하지 않는다.

플러그인에 전체 운영규정 사본을 고정 저장하기보다 최신 공식 원본을 읽는 절차를 우선한다.

## 10. 정상 시작 판정
새 직원/AI가 아래 질문에 대표의 도움 없이 답할 수 있어야 한다.
- AI 운영규칙 공식 원본은 어디인가?
- 현재 프로젝트와 등록 대기 프로젝트는 어디에서 확인하는가?
- 이 프로젝트의 Drive 폴더와 PROJECT_READ는 어디인가?
- 현재 상태와 다음 할 일은 무엇인가?
- 계정·SNS 접근정보는 어디에서 확인하는가?
- 중앙 INDEX는 누가 수정하는가?
- 내가 접근할 수 없는 시스템은 무엇인가?

## 11. 금지
- 비밀번호·OTP·복구코드를 운영문서에 기록하지 않는다.
- GitHub/Drive에 같은 AI 규칙의 중복 원본을 만들지 않는다.
- 권한이 없다고 개인 계정 자격증명을 다른 직원에게 공유하지 않는다.
- 접근 실패를 이유로 중복 프로젝트·중복 파일을 새로 만들지 않는다.
