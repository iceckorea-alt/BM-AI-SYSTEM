## 2. 새 채팅·새 작업 시작 절차
BM 업무를 새 채팅에서 시작할 때 다음 순서를 따른다.

1. Google Shared Drive 루트의 `BM_STARTER.md`를 읽는다.
2. GitHub의 `BM_DIGITAL_1.0.md`와 `BM_AI_AGENTS_.md` 최신본을 확인한다.
3. 프로젝트 업무이면 Google Sheets `BM_PROJECT_INDEX`의 `프로젝트`, `업데이트요청`, `레거시_폴더`를 필요한 범위에서 확인한다.
4. 해당 프로젝트의 Google Drive PROJECT_READ를 읽는다.
5. 브랜드·분야별 기준과 실제 업무 원본을 확인한다.
6. 업무를 수행한다.

동일 채팅에서 이미 확인했고 변경 가능성이 낮은 지침은 불필요하게 반복해서 전부 읽지 않는다. 다만 업무 범위가 바뀌거나 규정 변경 가능성이 있으면 재확인한다.

수정 직전에는 대상 PROJECT_READ, INDEX 행·요청, 실제 원본의 최신 상태를 다시 읽는다.

## 4. 사실확인

반드시 확인하는 경우:
- 주관 조직·운영단위·계약·회계 관계가 불명확
- 기존 프로젝트와 신규 프로젝트가 같은지 불명확
- 예산·계약·일정 등 핵심값이 충돌
- 법인·단체 경계가 불명확
- 삭제·대량이동·공유권한 변경 필요
- 상위 규정과 현재 요청이 충돌

아직 확정되지 않은 값은 `미확정`, `검토 중`, `제안`, `확인 필요` 등으로 구분한다.

AI는 스스로 시스템관리 역할을 부여하지 않는다.

## 6. PROJECT_READ 운영
- 실제 PROJECT_READ는 각 Google Drive 프로젝트 폴더에 둔다.
- 공식 증빙 원본이 아니라 Project Memory File이다.
- 현재 상태·결정·다음 행동·핵심 원본 위치를 유지한다.
- `현재 상태 저장`, `현재 상태 업데이트`, `READ 업데이트`, `작업 결과 저장`은 같은 저장 명령으로 처리한다.
- 수정 직전에 최신 READ를 다시 확인한다.
- 다른 AI·직원·세션 변경과 충돌하면 자동 덮어쓰기하지 않는다.
- 주요 일정·예산·담당자·범위·결정·완료업무·다음 행동·핵심 링크·단계 변화 등 새로 확정된 내용만 반영한다.
- 아이디어·초안·검토 중 수치·단순 파일 열람·브레인스토밍을 확정 사실처럼 기록하지 않는다.
- 사용자가 미확정 내용 저장을 요청하면 `검토 중`, `제안`, `확인 필요`로 명확히 구분하고 관련 초안 링크를 연결할 수 있다.
- 잘못된 기록은 삭제보다 정정 이력을 남긴다.
- 공식 원본과 충돌하면 공식 원본을 우선하고 READ를 정정한다.
- 모든 대화 내용을 READ에 복사하지 않는다.

### 6.1 작업 결과 저장의 의미
저장 시 다음을 점검한다.
- 확정된 결정사항
- 실제 완료된 업무와 결과물 링크
- 현재 진행상태와 미결사항
- 다음 해야 할 일

**결과물 파일 저장과 READ 갱신은 별도 상태다.** READ에 링크를 적은 것만으로 결과물 파일까지 저장됐다고 보고하지 않는다.

### 6.2 중간 저장
중요한 결정이 확정되거나 실제 결과물 저장·핵심 업무 완료가 확인되면, 승인된 편집 범위에서 READ에 반영한다. 긴 작업을 마지막 저장 한 번에만 의존하지 않는다.

### 6.3 종료 점검
완료보고 전에 이번 작업에서 새로 확정된 변화가 READ에 반영됐는지 확인한다.

### 6.4 저장 후 재확인
쓰기 성공 응답만으로 저장 완료를 판단하지 않는다. 최신 READ를 다시 읽어 해당 내용과 링크가 실제 반영됐는지 확인한다.

### 6.5 저장 실패
안전한 범위에서 원인을 확인하고 재시도한다. 계속 실패하면 실제 업무 완료와 기록 미완료를 구분해 보고하고, 복구해야 할 내용을 대화에 남긴다.

### 6.6 완료보고의 저장 상태
완료보고에는 다음 중 하나를 반드시 포함한다.
- `READ 저장·확인 완료`
- `READ 변경 없음`
- `READ 저장 미완료 — 사유와 복구할 내용`

자동 저장과 재확인이 이미 끝났다면 사용자에게 저장 명령을 다시 요구하지 않는다.

## 7. BM_PROJECT_INDEX 운영
공식 원본은 Google Sheets `BM_PROJECT_INDEX`다.

### 탭 역할
- `프로젝트`: Digital 1.0에서 정규 관리하는 프로젝트의 공식 행 목록
- `레거시_폴더`: 기존 Drive의 과거 프로젝트성 폴더 위치 목록
- `업데이트요청`: 신규 등록·변경 요청 큐

### 프로젝트 ID
- 형식: `BM-YYYY-NNN`
- 연도별로 001부터 순차 부여한다.
- 한번 부여한 ID는 프로젝트명이나 폴더명이 바뀌어도 변경하지 않는다.

### 중앙 INDEX 단일 작성자 원칙
- `프로젝트` 탭은 지정 시스템관리 AI 또는 권한 있는 관리자만 수정한다.
- 일반 직원 AI·프로젝트 AI는 `프로젝트` 탭을 직접 수정하지 않는다.
- 변경이 필요하면 `업데이트요청` 탭에 한 요청당 한 변경사항을 추가한다.
- 시스템관리 AI는 처리 직전에 INDEX 행, PROJECT_READ, 근거 원본을 다시 확인한다.
- 반영 시 `INDEX 최종수정일`, `수정자`, `행 버전`을 갱신하고 행 버전을 1 증가시킨다.
- 처리 후 요청 상태를 `반영` 또는 `반려`로 바꾸고 처리자·처리일시를 기록한다.
- 동일 프로젝트의 복수 요청은 현재 행 버전과 근거 원본을 기준으로 순차 처리한다.

## 8. 시스템별 실행

### Google Shared Drive
- 사업·프로젝트 실무자료와 실제 PROJECT_READ의 공식 위치다.
- 동일·유사 파일을 먼저 검색한다.
- 여러 위치에서 필요하면 복사보다 링크·바로가기를 우선한다.
- 루트에 개별 프로젝트나 임시파일을 직접 만들지 않는다.

### GitHub
- AI 운영지침·AI 직원 역할·Skills·자동화 코드·API/MCP 연동 문서·시스템 변경이력의 공식 원본이다.
- 저장소 `iceckorea-alt/BM-AI-SYSTEM`은 Public이며 읽기는 공개되어 있다.
- 운영규칙을 Drive에 동일 원본으로 복제하지 않는다.
- 비밀키·토큰·비밀번호를 저장하지 않는다.

### Airtable
- `BM_ACCESS_REGISTRY`에서 계정·SNS·서비스 접속정보와 접근권한을 관리한다.
- `계정정보`의 서비스 관리자 표기만으로 현재 AI의 실제 편집 권한이 확인됐다고 간주하지 않는다.
- `접근권한`에는 실제 확인한 접근수준만 기록한다.
- 비밀번호·OTP 비밀키·복구코드는 저장하지 않는다.

### Docswave
- 전자결재·기안·품의·지출·인사·근태의 공식 행정원본이다.
- Drive에 행정문서의 이중 공식 원본을 만들지 않는다.

### Canva
- 디자인 제작·편집 원본이다.
- 중간 시안을 Drive에 반복 저장하지 않는다.
- 최종 승인·납품·보존이 필요한 산출물만 Drive 정식 위치에 저장한다.

### Gmail / Calendar / Slack / Notion
- Gmail: 외부 커뮤니케이션
- Calendar: 공식 일정·행사·회의·마감
- Slack: 빠른 협의·알림
- Notion: 할 일·담당자·진척
- 중요한 확정 결정은 필요한 공식 원본 또는 READ에 반영한다.

### ChatGPT / Work / 외부 AI 에이전트
- 조사·분석·작성·실행 작업공간이다.
- 채팅기억 자체를 프로젝트 공식 기억으로 보지 않는다.
- 접근하지 못한 시스템을 접근한 것처럼 표현하지 않는다.

## 9. 인증정보·민감파일 처리
일반 지침·READ 탐색에서 인증파일·비밀키·토큰·비밀번호·복구코드 파일은 제외한다.

예: `client_secret*.json`, `credentials*.json`, 토큰 파일 등 인증정보로 보이는 파일을 일반 업무 목적으로 열거나 내용을 복사하지 않는다.

인증정보로 보이는 파일이 발견되면:
- 내용을 열지 않는다.
- READ·플러그인·Public GitHub에 복사하지 않는다.
- 보관 위치와 접근범위 정비 필요성을 별도 보고한다.
- 사용자 승인 없이 삭제·이동·공유권한 변경을 하지 않는다.

## 10. 파일명·버전·중복
Google Docs/Sheets/Slides는 자체 버전기록을 우선한다. 외부 파일은 필요한 경우에만 v01, v02를 사용한다.

피해야 할 이름:
- 최종2
- 진짜최종
- 복사본
- (1)(1)

권장 일반 파일명: `YYYYMMDD_문서종류_프로젝트명_설명.ext`

## 11. 이동·취소·삭제
- 프로젝트 전체 이동은 승인 후 수행하고 INDEX·READ 링크를 점검한다.
- 실제 기록이 있는 취소 프로젝트는 삭제하지 않고 상태를 `취소`로 관리한다.
- 공식 기록은 자동 삭제하지 않는다.
- 중복·임시파일은 삭제 후보와 보존 대상을 구분한 뒤 승인받는다.
- 삭제 후 끊어진 INDEX·READ 링크가 없는지 확인한다.

## 12. 보안
- 허용된 범위의 자료만 읽고 접근권한을 우회하지 않는다.
- 공유범위·관리자권한·대량이동·삭제 등 되돌리기 어려운 변경은 권한 있는 사용자 또는 지정 승인권자의 승인을 받는다.
- 고위험 비밀정보는 운영문서·READ·Airtable·GitHub에 기록하지 않는다.

## 13. 프로젝트 채팅
기본 흐름은 `STARTER → GitHub 최신 규칙 → INDEX → READ → 실제 원본 → 작업 → 저장·재확인`이다.

다음 세션은 이전 채팅 전체를 기억한다고 가정하지 않고 공식 원본에서 다시 시작한다.

## 15. 접근 실패 처리
- Drive, GitHub, Airtable, Docswave, Canva 등 필요한 시스템에 접근할 수 없으면 자료가 없다고 단정하지 않는다.
- 성공한 시스템과 실패한 시스템을 구분해 보고한다.
- 접근 실패한 시스템과 필요한 권한을 명시하고, 접근 가능한 공식 원본으로 가능한 범위만 수행한다.
- GitHub는 Public이지만 Shared Drive, Airtable, Docswave 등은 직원·에이전트별 연결 또는 권한이 별도로 필요할 수 있다.
- 권한을 우회하거나 개인 계정의 비밀정보를 공유해 해결하지 않는다.
