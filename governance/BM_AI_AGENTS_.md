## 6. PROJECT_READ 운영
- 실제 PROJECT_READ는 각 Google Drive 프로젝트 폴더에 둔다.
- 공식 증빙 원본이 아니라 Project Memory File이다.
- 현재 상태·결정·다음 행동·핵심 원본 위치를 유지한다.
- `현재 상태 저장`, `현재 상태 업데이트`, `READ 업데이트`는 같은 의미다.
- 수정 직전에 최신 READ를 다시 확인한다.
- 다른 AI·직원·세션 변경과 충돌하면 자동 덮어쓰기하지 않는다.
- 주요 일정·예산·담당자·범위·결정·완료업무·다음 행동·핵심 링크·단계 변화 등 새로 확정된 내용만 반영한다.
- 단순 문장 다듬기, 파일 열람, 브레인스토밍, 확정 전 수치는 기록하지 않는다.
- 잘못된 기록은 삭제보다 정정 이력을 남긴다.
- 공식 원본과 충돌하면 공식 원본을 우선하고 READ를 정정한다.

## 7. BM_PROJECT_INDEX 운영
공식 원본은 Google Sheets `BM_PROJECT_INDEX`다.

기본 필드:
- 프로젝트 ID
- 프로젝트명
- 운영 조직
- 담당자
- 담당 AI 직원
- 시작일
- 종료일
- 진행상태
- Google Drive 폴더 URL
- PROJECT_READ URL
- GitHub 관련 지침 URL
- 최종 수정일
- 주요 진행사항

갱신 대상:
- 새 프로젝트
- 프로젝트명·조직·담당자·담당 AI 변경
- 시작일·종료일·진행상태 변경
- Drive·READ·GitHub 링크 변경
- 주요 진행사항의 핵심 변화

프로젝트당 한 행을 원칙으로 하며, 수정 직전에 최신 행을 확인하고 중복 행을 만들지 않는다.

### 7.1 프로젝트 ID
- 형식: `BM-YYYY-NNN`
- 연도별로 001부터 순차 부여한다.
- 한번 부여한 ID는 프로젝트명이나 폴더명이 바뀌어도 변경하지 않는다.

### 7.2 다중 AI 충돌방지 — 단일 작성자 원칙
- 모든 AI는 INDEX를 읽을 수 있으나, 프로젝트 행의 쓰기는 `담당 AI 직원` 또는 지정 시스템관리 AI만 수행한다.
- `담당 AI 직원`이 `미지정`이면 지정 시스템관리 AI 외에는 INDEX를 수정하지 않는다.
- 프로젝트명·주관 조직·운영단위·Drive/READ 링크 같은 구조 필드는 지정 시스템관리 AI 또는 권한 있는 사용자가 수정한다.
- 일반 프로젝트 AI는 자기 프로젝트의 상태·주요 진행사항 등 허용된 값만 수정한다.
- 쓰기 직전에 해당 행을 다시 읽고 `행 버전`을 확인한다.
- 수정 시 `INDEX 최종수정일`, `수정자`, `행 버전`을 함께 갱신하고 행 버전을 1 증가시킨다.
- 읽은 뒤 행 버전이 바뀌었거나 다른 수정 흔적이 있으면 쓰기를 중단하고 최신 행을 다시 읽는다.
- 행 전체 덮어쓰기를 피하고 필요한 셀만 수정한다.
- 동시에 같은 프로젝트를 수정할 필요가 있으면 한 AI가 대표 작성자가 되고 다른 AI는 결과를 전달한다.

> Google Sheets 자체에는 강제적인 트랜잭션 잠금이 없으므로, 위 단일 작성자 규칙을 지키지 않는 동시 쓰기는 완전한 충돌방지를 보장하지 못한다.

## 8. 시스템별 실행

### Google Shared Drive
- 사업·프로젝트 실무자료와 실제 PROJECT_READ의 공식 위치다.
- 동일·유사 파일을 먼저 검색한다.
- 여러 위치에서 필요하면 복사보다 링크·바로가기를 우선한다.
- 루트에 개별 프로젝트나 임시파일을 직접 만들지 않는다.

### GitHub
- AI 운영지침·AI 직원 역할·Skills·자동화 코드·API/MCP 연동 문서·시스템 변경이력의 공식 원본이다.
- 운영규칙을 Drive에 동일 원본으로 복제하지 않는다.
- 비밀키·토큰·비밀번호를 저장하지 않는다.

### Airtable
- 계정·SNS·서비스 접속정보 등 공통 기준정보를 관리한다.
- 비밀번호·OTP 비밀키·복구코드는 저장하지 않는다.
- 과거 대화나 AI 기억보다 최신 확정 레코드를 우선한다.

### Docswave
- 전자결재·기안·품의·지출·인사·근태의 공식 행정원본이다.
- Drive에 행정문서의 이중 공식 원본을 만들지 않는다.
- READ에는 필요한 문서번호·상태·핵심 결정·원본 링크만 연결한다.

### Canva
- 디자인 제작·편집 원본이다.
- 중간 시안을 Drive에 반복 저장하지 않는다.
- 최종 승인·납품·보존이 필요한 산출물만 Drive 정식 위치에 저장한다.

### Gmail / Calendar / Slack / Notion
- Gmail: 외부 커뮤니케이션
- Calendar: 공식 일정·행사·회의·마감
- Slack: 빠른 협의·알림
- Notion: 할 일·담당자·진척
- 중요한 확정 결정은 필요한 공식 원본 또는 READ에 반영한다.

### ChatGPT / Work
- 조사·분석·작성·실행 작업공간이다.
- 채팅기억 자체를 프로젝트 공식 기억으로 보지 않는다.

## 10. 이동·취소·삭제
- 프로젝트 전체 이동은 승인 후 수행하고 INDEX·READ 링크를 점검한다.
- 실제 기록이 있는 취소 프로젝트는 삭제하지 않고 상태를 `취소`로 관리한다.
- 공식 기록은 자동 삭제하지 않는다.
- 중복·임시파일은 삭제 후보와 보존 대상을 구분한 뒤 승인받는다.
- 삭제 후 끊어진 INDEX·READ 링크가 없는지 확인한다.

## 11. 보안
- 허용된 범위의 자료만 읽고 접근권한을 우회하지 않는다.
- 공유범위·관리자권한·대량이동·삭제 등 되돌리기 어려운 변경은 권한 있는 사용자 또는 지정 승인권자의 승인을 받는다.
- 고위험 비밀정보는 운영문서·READ·Airtable·GitHub에 기록하지 않는다.

다음 세션은 이전 채팅 전체를 기억한다고 가정하지 않고 INDEX와 READ에서 다시 시작한다.

## 14. 업무환경 개선
AI는 다음을 개선 후보로 본다.
- 같은 자료 반복 탐색
- 파일명·폴더명 때문에 검색 실패
- INDEX·READ·원본 연결 단절
- 중복정보로 최신본 불명확
- 사용자가 매번 저장위치나 과거 결정을 설명
- 실제 Drive 구조와 운영규칙 불일치
- 반복업무를 매번 처음부터 수작업

안전한 작은 정리는 업무와 함께 처리할 수 있지만, 구조·권한·타인의 업무방식에 영향을 주는 변경은 승인 후 수행한다.

## 15. 접근 실패 처리
- Drive, GitHub, Airtable, Docswave, Canva 등 필요한 시스템에 접근할 수 없으면 자료가 없다고 단정하지 않는다.
- 접근 실패한 시스템과 필요한 권한을 명시하고, 접근 가능한 공식 원본으로 가능한 범위만 수행한다.
- 비공개 GitHub 저장소, Shared Drive, Airtable Base는 직원별 계정·에이전트 연결 권한이 별도로 필요할 수 있다.
- 권한을 우회하거나 개인 계정의 비밀정보를 공유해 해결하지 않는다.
