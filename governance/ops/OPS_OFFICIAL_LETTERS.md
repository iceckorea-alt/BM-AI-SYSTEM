# OPS_OFFICIAL_LETTERS — 공문관리

규정 v3.18 · 2026-11-18 · 인터뷰 합의에 따른 작업지시서 겸 운영 원본. 내부 원장 링크는 비공개 INDEX 공통문서에만 둔다.

## 0. 목적·진입
서울·인천 공문의 번호·승인된 현재 원본·실제 발송·후속 업무를 한 곳에서 확인하고 번호 중복·미발송·중복 발송을 줄인다. STARTER → INDEX 공통문서 → 별도 BM_공문대장. 발신/수신은 같은 파일의 별도 탭이며 실제 공문 파일은 실무 폴더에 보관한다.

## 1. 작성·등록·번호
공문 작성 요청은 기존 기록을 확인하고 발행주체·수신기관/부서·To/CC·목적/내용·관련 업무·시행일/회신기한·담당·중간검토자/직책·최종승인자·붙임 중 빠진 것만 질문한다. 서울/인천 지정 HWPX 공문서식을 복사하여 표·결재란을 유지하고 실제 한글에서 쪽/칸을 검증한다. 오래된 번호·날짜·담당·기입 내용·직인을 새 공문에 재사용하지 않는다.

작성 때 BMS/BMI·시행연도를 확인해 예정번호를 안내하되 이 단계는 번호 확정/대장 등록이 아니다. 초안은 INDEX 할일에서 관리한다. 최종승인 후 번호 재조회·중복 확인→번호 확정과 발신대장 등록→날인·발송 PDF 준비. 번호 변경으로 승인 문서의 표시가 달라지면 최종 확인을 다시 받는다. 일부 이력·파일명만 보고 다음 번호를 확정하지 않는다. 취소번호는 사유와 함께 보존하고 재사용하지 않는다.

현재 자동 채번 잠금은 미설치다. 번호 확정은 단일 창구에서 한 건씩 처리하고 쓰기 직전/직후 번호·관리ID를 재조회한다. 여러 AI의 동시 자동 발급을 허용하지 않는다. 향후 잠금 구현·실제 동시 실행 검증 전에는 모의 직렬 처리 검증을 실운영 보장으로 설명하지 않는다.

## 2. 검토·파일·보관
비엠 최종검토/결재는 대표. 중간검토자가 없으면 담당→최종승인. 향후 경의선 운영 조직은 센터장이 최종승인자이나 실제 운영 시작·발행명칭/번호·계정 변경/권한 매핑은 추후 설계다. 예정 승인자 이름과 실제 승인 증거를 구분한다.

실무 공문은 프로젝트 02_대외·계약/공문, 제안 단계는 해당 제안건/공문, 일반 업무는 소속 DOC/공문을 사용한다. 기존 파일은 이번 대장 통합을 이유로 이동·삭제하지 않는다. 원본 위치가 다르면 실제 위치를 기록하고 재정리는 별도 지시로 한다. 대장에 보관폴더·HWPX·최종 PDF·발송메일을 연결한다.

승인된 HWPX와 날인 PDF를 함께 보관한다. 중요 변경은 재승인하며 같은 문서번호로 수정본을 발송한다. 새 버전ID·변경요약·승인근거/대상 버전·승인시각·날인 확인을 문서버전에 추가하고 이전 파일/발송 이력을 보존한다. 현재버전ID를 바꿔 이전 버전의 발송 완료가 새 수정본에 승계되지 않게 한다. 새 요청이나 철회에 해당하는지는 최종승인자가 판단한다.

## 3. 이메일·붙임·발송이력
메일 제목에 [문서번호]를 넣고 수정본은 [수정본] 표시와 변경 요약을 적는다. 한 공문에 여러 수신기관을 적고 같은 내용/PDF를 To·CC에 넣어 메일 한 건으로 발송할 수 있다. 발송이력 한 행은 실제 메일 한 건이며 기관 수만큼 복제하지 않는다. 임시보관/문안 준비는 발송 완료가 아니다.

info@ 연결 AI는 요청 범위에서 승인 PDF·붙임·수신처·메일 본문을 임시보관하고 준비 사실을 알린다. 연결 없는 직원 AI는 문안/PDF를 준비하고 직원이 직접 첨부한다. 실제 전송은 사람이 한다. 이 공문대장이 Gmail 초안 저장·메일 전송을 자동 실행하지는 않는다. 실제 보낸편지함 메일ID·링크·전송시각과 첨부 PDF 버전을 확인한 후 발송 완료를 기록한다. 연결 실패·전언만 있으면 미확인으로 남긴다.

붙임은 발송 메일의 첨부를 기본 증빙으로 하고 원래 위치를 유지한다. 중요한 자료만 별도 보존하며 발송 전 목록·파일·버전을 대조한다. 반송은 해당 주소·사유·후속조치를 같은 메일 기록에 남기고 새 전송은 새 발송ID/메일ID 행에 기록한다. 최초·수정본·재발송을 구분하고 이전 원본을 덮어쓰지 않는다. 이미 존재하는 메일ID·발송ID·기록순번 중복을 확인한다.

## 4. 탭·단일 원본 계약
- 발신대장: 공문 한 건 한 줄. 결재 후 번호 확정 시 등록. 시행일은 공문 기재일이며 발송일시는 실제 전송시각이다. 관리ID는 번호가 바뀌어도 유지한다.
- 문서버전: 버전 한 건 한 줄. HWPX/PDF·변경요약·승인/날인/붙임 근거를 보존한다. 발신 I/J는 현재버전ID로 조회하고 과거 버전을 덮어쓰지 않는다.
- 발송이력: 메일/준비 기록 한 건 한 줄. A 발송ID, B 공문관리ID, C 버전ID, E 처리결과, F/G 보낸메일ID/링크, H 실제 전송시각, I/J To/CC, L 첨부 PDF, N 반송, P 임시보관 링크, S 고정 기록순번. S는 전체 이력에서 단조 증가하는 고정 숫자이며 정렬 후 재번호화하지 않는다. 임시보관을 실제로 보낸 경우 같은 기록에 전송 증거를 채운다.
- 공문연결: 발신관리ID↔수신접수ID 한 쌍 한 줄. 다대다 허용, 중복 연결 금지. 양 대장에서 연결 건수를 조회한다.
- 수신대장: 기관의 첨부 공문만 접수. 본문만 있는 요청·일반 홍보 제외. 상대 문서번호와 비엠 접수번호 구분. 메일 담당 AI가 접수하고 조치 필요 건을 알리는 운영안이나 자동 접수기는 미구현이다. 상세 수신 기준은 추가 인터뷰 대상이다.

발신 A:F/H/N:Z/AC:AD는 등록·관리값, G/I:M/AA:AB/AE:AF는 자동 보기다. W 관리ID, X 현재버전ID, Y 관리상태, Z 정정/취소사유. G 상태·K/L 전송증거는 현재 버전의 발송이력에서 계산한다. 자동 셀을 값으로 덮어쓰지 않는다. 1000행 범위를 넘기면 수식·검증·조건부 서식을 함께 확장한다. 기술 열·공문연결·검증기록은 평소 숨길 수 있다.

## 5. 회신·INDEX·Calendar
회신기한은 발신대장에 기록, 실행 과제는 INDEX 할일에 한 번만 만들고 링크한다. 일부 회신·자료 보완은 완료로 처리하지 않는다. 수신공문에 회신한 사실과 그 수신 건의 처리 완료는 구분한다.

기한은 캘린더에도 표시하고 기본 3일 전·당일 알림. 설정 전에는 캘린더 등록 대기로 두며 실제 이벤트 확인 후만 등록 확인으로 바꾼다. 급한 건은 별도 조정, 3일 전이 지났으면 즉시 확인하여 과거 알림을 만들지 않는다. 기한 변경·취소 때 연결된 INDEX/이벤트도 대조한다. 이번 배포는 Calendar 연결을 생성하지 않았다.

## 6. 검증·통합·한계
운영 규칙 38개 모의 시뮬레이션과 실제 Sheets의 임시보관/발송 날짜·링크/반송/수정버전 미승계/번호중복/다대다 연결 수식을 검증한다. 시험 행은 제거한다. 기존 기록은 관리ID·번호·시행일·제목·수신처·담당·중간/최종역할·발송방법·파일위치·미확정 근거를 대조 이관한다. 과거 승인·발송을 추정하지 않는다.

사용자의 기존 대장 삭제 지시는 구 공문대장만 대상이며 실제 공문·수정본·증빙은 제외한다. 이관·재조회·현행 안내 링크 갱신 후 구 대장 파일/탭을 정리한다. 과거 LOG/구 버전 공지는 고쳐 쓰지 않고 최신 변경 공지로 대체를 안내한다. 일반 문서관리·견적·서식·메일수집 기능은 보존한다.

번호 잠금·권한자 계정 검증·Gmail 자동 실행·수신 자동 접수·Calendar 실제 등록/알림은 실가동 미검증/미구현이다. 시트 경고는 발송 강제 차단 장치가 아니다. 설치·운영 완료를 허위로 보고하지 않는다.
