# BM_CORE — BM AI 공통 조약

규정 v3.1 · 2026-10-21 · 모든 AI·직원이 BM 업무 시작 시 매번 읽는 유일한 규정. 상세는 업무별 OPS 파일에 있고, 필요할 때만 읽는다.

## 1. 시작 순서
`BM_STARTER(Drive) → BM_CORE → [업무별 OPS] → BM_PROJECT_INDEX → PROJECT_READ(0장 요약 기준) → 필요한 원본만` (LOG는 경위가 필요할 때만)
- 같은 채팅에서 이미 읽은 규정은 다시 읽지 않는다. 수정 직전에는 대상 READ·INDEX 행만 최신본을 다시 읽는다.
- 채팅 기억은 공식 기억이 아니다. 새 채팅은 공식 원본에서 다시 시작한다.

## 2. 원본 위치 (원본 1개 · 위치 1곳 · 링크는 여러 곳)
AI 규정=GitHub / 프로젝트 목록=Sheets `BM_PROJECT_INDEX` / 프로젝트 기억=Drive `PROJECT_READ` / 실무자료·산출물=Shared Drive `BM` / 계정·권한=Airtable `BM_ACCESS_REGISTRY` / 결재·인사·회계=Docswave / 디자인=Canva / 일정=Calendar / 대외소통=Gmail

## 3. 역할과 권한
| 역할 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| 대표 | 모든 결정, 마감·종료 승인, 역할·권한 부여 | — |
| 시스템관리 | INDEX 등록·ID·종료·취소, GitHub 규정 반영, 권한대장 관리 | 프로젝트 내용 결정 |
| 프로젝트 책임자 | 자기 프로젝트 READ 0장·상태, 할 일 배정, 자기 INDEX 행의 허용 열 갱신, 마감요청 | 종료 처리, [대표결정] 변경 |
| 참여자 | 자기 담당 할 일 갱신, LOG 추가, [제안] 기록 | 0장·상태 변경, 남의 줄 수정 |

- AI는 지시한 사람과 같은 권한만 가진다. 스스로 역할을 부여하지 않는다.
- AI는 직원이 아니라 사람이 쓰는 도구다. 권한과 책임은 지시한 사람에게 있다.
- 현재 인원·역할 지정은 Drive `BM_STARTER` 2장에 둔다(실명은 Public GitHub에 쓰지 않는다). 책임자 미지정 프로젝트는 대표가 책임자.

## 4. 작성자는 실명
- 모든 기록의 작성자·결정 주체·담당은 사람의 실명으로 쓴다. AI 이름은 작성자가 아니다.
- AI가 대신 적은 줄은 실명 뒤에 도구를 작게 표시한다: `홍길동 (Claude 기록)`, `홍길동 (GPT 기록)`. 사람이 직접 적으면 실명만.
- 대상: READ의 결정사항·할 일, LOG, INDEX `수정자`, 업데이트요청 `요청자`.
- 지시한 사람을 모르면 쓰기 전에 묻는다.

## 5. 결정 등급
- `[대표결정]` `[책임자결정]` `[제안]` 중 하나를 결정사항에 붙인다.
- 예산·계약·대외 공문·행사 일정·장소·프로젝트 생성/종료/취소는 `[대표결정]`이 있어야 확정이다. 그 전에는 `[제안]`으로만 기록하고 대표 확인을 요청한다.
- 아이디어·초안·AI 추천은 확정이 아니다. 확인 안 된 값은 `미확정`으로 둔다. 추정으로 채우지 않는다.

## 6. 저장 — READ는 현재, LOG는 이력
- 프로젝트마다 두 문서를 둔다: `YYYY_프로젝트명_READ`(지금 유효한 최종 상태만) / `YYYY_프로젝트명_LOG`(바뀐 기록, 추가만 함). 둘 다 같은 프로젝트 폴더.
- 확정된 결정·완료·상태 변화는 저장 명령 없이 즉시 반영한다. (`작업 결과 저장` 등은 수동 저장 명령으로도 유효)
- 값이 바뀌면 READ는 새 값으로 덮어쓰고 과거 값 흔적(→, 기존, 정정 등)을 남기지 않는다. 대신 LOG 끝에 한 줄 추가: `YYYY-MM-DD · 실명(도구) · 항목: 이전값 → 새값 · 이유/근거`. 새 항목·완료도 같은 형식으로 LOG에 남긴다.
- LOG는 문서 끝에 덧붙이는 방식으로 쓰고, 평소에는 읽지 않는다(경위·당초 계획 확인, 결과보고 작성 때만).
- 쓰기 순서: 최신본 다시 읽기 → 바뀐 줄만 수정(문서 전체 재작성 금지) → 다시 읽어 반영 확인.
- 다른 사람·AI의 수정과 충돌하면 덮어쓰지 않고 차이를 보고한다. 잘못된 기록은 READ에서 바로잡고 LOG에 정정 사유를 남긴다.
- 결과물 파일 저장과 READ 기록은 따로 확인한다.
- 문서에 쓸 수 없는 AI(읽기 전용 연결)는 READ·LOG·INDEX에 넣을 줄을 붙여넣기 가능한 형태로 제시하고 `READ 저장 미완료 — 쓰기 권한 없음`으로 보고한다. 사람이 붙여넣으면 작성자는 그 사람 실명.
- 0장 요약의 상태·다음 할 일이 바뀌면 INDEX 같은 행의 `진행상태`·`다음 할 일`도 맞추고 `수정자`(실명)·`수정일`·`행 버전`을 갱신한다(권한 없으면 업데이트요청).
- 긴 파일은 쪼개서 필요할 때만 읽는다: READ가 길어지면(약 6,000자 초과) 참조용 상세는 같은 폴더 `_부록` 문서로 옮기고 READ 6장에 링크한다. 규정도 같은 원칙으로 CORE는 짧게, 상세는 OPS 파일로 둔다.
- 전체 구조 개편 같은 큰 변경 전에만 `99_시스템백업`에 문서 사본을 만든다. 통째 복원은 Google 문서 버전 기록으로 한다.

## 7. 금지·승인
- 삭제·대량이동·공유범위·관리자권한 변경은 대표 승인 후에만 한다.
- 비밀번호·OTP·복구코드·API Secret·토큰·계좌/주민번호를 어디에도 저장하지 않는다. 인증파일(`client_secret*`, credentials, token)은 열지 않는다.
- Public GitHub에 개인정보·계정정보·내부 리소스 ID를 넣지 않는다.
- 권한을 우회하지 않는다. 접근 실패는 `자료 없음`이 아니라 실패로 보고한다.
