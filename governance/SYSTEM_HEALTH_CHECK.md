# SYSTEM_HEALTH_CHECK — 정기 점검표

규정 v3.1 · 2026-10-21 · 점검할 때만 읽는다. 규칙 설명은 하지 않고 확인 항목만 둔다. 보고는 `확인 완료 / 수정 완료 / 미검증 / 사용자 결정 필요`로 구분한다. 권한 때문에 확인 못 한 항목은 `미검증`.

## 1. 구조·입구
- [ ] Drive 루트에 `BM_STARTER`, `BM_PROJECT_INDEX`, 00_BM공통, 01_BM서울, 02_BM인천, 98_아카이브, 99_시스템백업만 있다
- [ ] STARTER가 BM_CORE raw 주소와 현재 규정 버전을 안내한다
- [ ] GitHub raw 주소로 BM_CORE·OPS·템플릿이 열린다
- [ ] 구형 운영문서가 archive·99_시스템백업에만 있고 현재 규정으로 혼동되지 않는다
- [ ] 같은 규칙이 두 파일 이상에 중복 서술되지 않았다
- [ ] BM_CORE가 A4 1쪽 분량을 넘지 않는다

## 2. INDEX·READ 정합성
- [ ] 정규 프로젝트 행의 Drive·READ 링크가 열린다
- [ ] INDEX `진행상태`·`다음 할 일`이 READ 0장과 일치한다
- [ ] 일정이 지난 프로젝트가 `진행`으로 방치되지 않았다
- [ ] `업데이트요청`에 오래된 `대기` 요청이 없다
- [ ] 진행 프로젝트마다 책임자가 지정돼 있다(미지정이면 대표)
- [ ] READ가 최신 템플릿 Schema를 따르고, 0장 요약이 있다
- [ ] READ 결정사항에 등급과 결정 주체(실명)가 있고, 각 프로젝트에 LOG가 있으며 READ 6장에 링크돼 있다
- [ ] READ에 과거 값 흔적(→, 기존, 정정)이 남아 있지 않다(이전 값은 LOG에)
- [ ] 변동 가능한 정보(도구명·모델명·견적)가 근거 없이 확정 사실로 남지 않았다

## 3. 저장 절차 (실제 시나리오로 검증)
- [ ] 확정 변경이 저장 명령 없이 READ에 반영되고, 쓰기 후 재확인됐다
- [ ] 변경 없는 업무에 `READ 변경 없음`이 표시됐다
- [ ] 결과물 파일 저장과 READ 기록을 따로 확인했다
- [ ] 저장 실패 시 업무 완료와 기록 미완료를 구분하고 복구할 내용을 남겼다

## 4. 권한·보안
- [ ] Public GitHub에 개인정보·계정정보·리소스 ID·인증정보가 없다
- [ ] Airtable `계정정보`에 비밀정보가 없고, `접근권한`에 실제 확인 수준·근거·미검증 사항이 있다
- [ ] 연결 성공·관리자 표기를 권한으로 확대 해석하지 않았다
- [ ] 각 시스템 접근 성공/실패를 구분해 보고했다
- [ ] 직원 업무정보와 비공개 인사정보가 분리돼 있다
- [ ] 인증파일로 보이는 파일을 열지 않았고, 발견 시 위치만 보고했다
- [ ] 퇴사·교체된 사람·AI의 권한이 회수됐다
- [ ] 투입된 모든 AI에 부트스트랩 지시가 설정돼 있고 콜드스타트 테스트를 통과했다

## 5. 마감
- [ ] `마감` 지시가 즉시 종료로 처리되지 않았다
- [ ] 대외 프로젝트 결과보고서가 실제 파일로 `05_성과·결과`에 있고 READ에 링크됐다
- [ ] 확인되지 않은 실적·예산·성과를 추정해 쓰지 않았다
- [ ] 결재 승인 전 `종료`로 바뀌지 않았고, 승인 후 INDEX·READ가 모두 `종료`다

## 6. 이상 발견 시
링크·표기·단일 원본 불일치처럼 안전한 것은 즉시 고치고 CHANGELOG에 남긴다. 삭제·공유권한·대량이동·법적/회계 사실은 승인 후 처리한다.
