## 확인 완료
- Google Shared Drive 루트의 공식 진입점은 `BM_STARTER.md`와 Google Sheets `BM_PROJECT_INDEX`다.
- 구형 Drive 운영 MD는 `99_시스템백업`에 LEGACY 이름으로 분리되어 공식 원본과 혼동되지 않는다.
- AI 운영규칙의 공식 원본은 Private GitHub `iceckorea-alt/BM-AI-SYSTEM`이다.
- 실제 Shared Drive 경로는 `02_BM서울_프로젝트`, `02_BM인천_프로젝트` 기준으로 GitHub 규칙과 일치한다.
- Google Sheets는 `프로젝트`, `레거시_폴더`, `업데이트요청` 3개 역할로 분리된다.
- 중앙 `프로젝트` 탭은 시스템관리 단일 작성자 방식으로 운영하고 다른 직원·AI는 `업데이트요청` 큐를 사용한다.
- 현재 2026 정규 프로젝트 2건은 INDEX와 PROJECT_READ의 프로젝트 ID·상태·대외명·Drive 링크가 정렬되어 있다.
- PROJECT_READ 템플릿은 Schema v1.2이며 실제 READ는 Google Drive의 Google Docs를 권장한다.
- 홍대 캔버스 공통 브랜드 READ의 구형 STARTER/INDEX/AGENTS 링크는 새 구조로 교체되었다.
- 홍대 축제 동일 설명회 PDF 5개는 본문이 동일함을 확인하여 1개를 원본 위치에 두고 4개를 중복자료 폴더로 분리했다.
- Airtable `BM_ACCESS_REGISTRY`는 `계정정보`와 `접근권한`을 분리하며 비밀번호·OTP·복구코드를 저장하지 않는다.

## 다중 AI 충돌방지
- 중앙 INDEX 직접 쓰기 경로를 시스템관리 AI/관리자로 단일화했다.
- 프로젝트 AI·직원 AI는 변경 요청을 큐에 남긴다.
- 시스템관리 AI는 INDEX 행·PROJECT_READ·근거 원본을 재확인한 뒤 순차 반영한다.
- 반영 시 수정자·최종수정일·행 버전을 갱신한다.
- PROJECT_READ는 담당/대표 작성자를 두고 수정 직전 최신본을 다시 읽는다.

## 남은 외부 의존성 — 중요
아래는 문서나 구조의 결함이 아니라 실제 사용자/에이전트 계정별 권한 문제다.

- GitHub 저장소가 Private이므로 다른 직원의 GitHub 계정이 접근권한을 받아야 한다.
- Google Shared Drive BM의 멤버 권한이 직원별로 확인돼야 한다.
- Airtable BM_ACCESS_REGISTRY의 접근권한이 직원별로 확인돼야 한다.
- Docswave·Canva·Gmail·Calendar는 맡은 업무에 따라 별도 접근권한이 필요하다.
- 각 새 AI의 시작 설정에는 최소한 “BM Shared Drive 루트의 BM_STARTER.md부터 읽는다”는 bootstrap 지시가 들어가야 한다.

직원 계정이 확정되면 Airtable `접근권한` 테이블에 실제 확인값을 기록한 뒤 투입한다. 권한이 없는 AI는 자료 부재로 추정하지 않고 권한 부족을 보고한다.

## 최종 원칙
구조적 충돌은 운영규칙으로 차단할 수 있지만, 연결되지 않은 외부 계정의 접근권한까지 문서만으로 보장할 수는 없다. 따라서 신규 직원·AI 투입 전 접근권한 확인을 배포 게이트로 사용한다.
