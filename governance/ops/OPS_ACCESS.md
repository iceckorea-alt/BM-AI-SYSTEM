# OPS_ACCESS — 계정·권한·보안

규정 v3.0 · 2026-10-21 · 계정·SNS·접속정보, 권한 확인, 인증파일, 접근 실패를 다룰 때만 읽는다. Airtable Base·Table ID는 Drive `BM_STARTER`에만 둔다(Public GitHub 금지).

## 1. Airtable `BM_ACCESS_REGISTRY`
- `계정정보`: 서비스명, 로그인 계정·업무용 이메일·GitHub 사용자명, 조직·워크스페이스, 접속주소, 상태, 최종 확인일, 비밀이 아닌 리소스 ID·설명.
- `접근권한`: 사람·AI 식별정보와 작성자 코드, 시스템별 실제 확인된 접근수준, 업무상 허용 범위, 최종 확인일, 확인 근거, 미검증 사항.
- 과거 대화보다 Airtable 최신 확정값이 우선이다. 처음 접속할 때는 구조·접근만 확인하고 계정정보 전체를 출력하지 않는다.

## 2. 권한은 실제로 확인한 만큼만
- 연결 성공, `관리자` 계정 표기, 대장 기록 어느 것도 실제 편집·관리 권한을 뜻하지 않는다. 실제 검증한 수준만 기록한다.
- '대표 전용' 표기·숨김 화면을 접근 제한 구현으로 보지 않는다. 직원 확대 전 Airtable Base/Interface/공유 권한으로 실제 제한이 되는지 검증하고, 안 되면 별도 Base 등 분리를 검토한다.
- 시스템 연결 ID는 대표와 시스템관리 중심, 로그인 계정정보는 대표와 해당 업무 담당에게 필요한 범위로 제한한다.

## 3. 직원 정보
- 업무 연결정보(이름·직책·업무용 이메일·담당 프로젝트·작성자 코드)와 비공개 인사정보(개인 연락처·주소·급여)를 분리한다.
- 공식 인사·급여·계약 원본은 Docswave다. Airtable에는 업무 연결에 필요한 최소 정보만 둔다.
- 직원 명부는 필요가 확정되기 전 미리 만들거나 추정해 채우지 않는다.

## 4. 인증정보·민감파일
- 비밀번호·OTP 비밀키·복구코드·API Secret·토큰·주민번호 전체·계좌 비밀번호는 GitHub·Drive 운영문서·READ·Airtable 어디에도 저장하지 않는다.
- `client_secret*.json`, credentials, token 등 인증파일로 보이는 파일은 열지 않는다. 파일명·위치 등 메타데이터만 확인한다.
- 발견 시: READ·플러그인·Public GitHub에 복사 금지 / 보관 위치·접근범위 정비 필요성만 보고 / 승인 없이 삭제·이동·권한 변경 금지.
- 권한이 없다고 개인 계정 자격증명을 다른 사람과 공유하지 않는다.

## 5. 접근 실패
- 필요한 시스템에 접근하지 못하면 자료가 없다고 단정하지 않는다. 성공·실패·미확인 시스템을 구분해 보고하고, 필요한 권한을 명시한다.
- 일부 실패 시 `비엠에 접속했습니다`처럼 전체 성공으로 표현하지 않는다.
- 접근 실패를 이유로 중복 프로젝트·중복 파일을 새로 만들지 않는다.
- 비공개 Drive·Airtable 자료를 검색엔진 등으로 우회 조회하지 않는다.

## 6. Public GitHub
저장소는 공개다. 직원 개인정보, 비공개 계정정보, Drive·Sheets·Airtable 리소스 ID, 인증정보를 커밋하지 않는다. 실수로 올렸다면 삭제 커밋만으로는 이력에 남으므로 대표에게 보고한다.
